# GomokuNNUE：Windows 本地五子棋训练与对弈工作台

Status: ready-for-agent
Updated: 2026-11-09
Scope: 项目重设计主规格；替代旧规格、旧 M5/M6 计划和旧实验门槛。
Delivery: 设计已整理；本文描述目标行为，不代表代码已经完成重构。

## Problem Statement

用户希望在自己的 Windows 电脑上，通过一个客户端完成有禁手五子棋的人机对弈、局面收集、从零训练、自我训练和历史版本测评，并让自己的模型逐步提高棋力。

现有实现已有棋盘、部分规则处理、搜索、训练和增量推理基础，但仍围绕旧网络、手工评估标签和旧实验门槛组织。它没有一站式 GUI，也没有接入 Rapfi 教师。旧文档把不做 GUI、旧网络结构及特定实验失败后的限制写成长期约束，已不符合本轮方向。

用户的目标是相对自己的历史版本进步，不要求战胜 Rapfi，也不以达到某个固定数据量作为训练前置条件。

## Solution

提供 Windows 本地运行的训练与对弈工作台。后端执行器统一负责棋盘、合法落子、禁手和胜负判定；算杀复用支持 Renju 的开源 VCF 实现；PyTorch 训练自己的价值网络；C++ 增量累加器和 Alpha-Beta 搜索负责实际对弈。

训练分为教师启动与无教师自主训练：

- 教师启动：收集多样局面，过滤已识别的算杀阶段局面，由 Rapfi 提供评分，训练出初始正式版本 v0。
- 自主训练：正式版本自我对弈，记录完整胜负，以对局结果训练候选模型，逐步停止新增教师标签，最终能够完全不调用 Rapfi。
- 棋力测评：候选版本挑战冻结的正式版本和选定历史版本，达到预先记录的晋级条件后才替换正式版本。与 Rapfi 对战不是交付要求。

采用少量数据启动、持续采集、滚动样本池、持续训练和周期测评的流水线。采集与训练可以并行，模型发布按版本边界进行。500万～2000万条可以是长期累计规模，不是启动门槛，也不是必须永久保留的数据量。

## User Stories

1. 作为本机用户，我希望在一个客户端进入对弈、采集、训练、自我训练和测评，以便完成整个流程而不必手动拼接脚本。
2. 作为玩家，我希望与自己训练出的正式版本对弈，以便直接体验当前模型的能力。
3. 作为玩家，我希望选择执黑或执白，以便体验两种规则角色。
4. 作为玩家，我希望看到合法落点及禁手原因，以便理解哪些操作可以执行。
5. 作为玩家，我希望准确判定黑棋恰好五连、白棋五连及以上和黑方禁手，以便获得一致的对局结果。
6. 作为玩家，我希望开始新局并查看已经结束的对局，以便复盘模型表现。
7. 作为开发者，我希望对弈、数据采集和测评使用同一套权威规则，以便避免不同模块对同一落点给出相反结论。
8. 作为开发者，我希望接入已有开源 VCF，以便不再自行开发算杀算法。
9. 作为用户，我希望算杀达到时间或节点上限时明确报告未知，以便不把未完成搜索误认为不存在杀棋。
10. 作为数据采集者，我希望产生合法且有差异的开局和中盘，以便避免数据被少量重复对局占满。
11. 作为数据采集者，我希望 Rapfi 使用与本项目一致的禁手规则，以便教师标签对应实际游戏。
12. 作为数据采集者，我希望过滤终局、已识别算杀局面及异常标签，以便价值网络重点学习非强制战术局面。
13. 作为数据采集者，我希望看到过滤原因、未知数量和有效样本数，以便了解真正可用于训练的数据。
14. 作为数据采集者，我希望保存局面对应的对局、行棋方、模型版本和标签来源，以便追溯训练样本。
15. 作为训练者，我希望小批量数据可用后即可启动训练，以便尽早发现链路问题。
16. 作为训练者，我希望采集与训练同时运行，以便持续利用新数据。
17. 作为训练者，我希望限制样本池容量并逐步淘汰旧样本，以便控制磁盘占用。
18. 作为训练者，我希望从不同对局的新旧样本中混合采样，以便降低局面相关性和遗忘。
19. 作为训练者，我希望八种棋盘对称变换用于训练，以便提高数据利用率。
20. 作为训练者，我希望验证集按对局隔离并排除对称等价泄漏，以便得到可信的学习指标。
21. 作为训练者，我希望从随机初始化训练自己的网络，以便得到来源明确的初始模型。
22. 作为训练者，我希望使用指定的单输出网络，以便在训练端和 C++ 部署端保持一致。
23. 作为训练者，我希望选择 MSE 或 SmoothL1 并记录配置，以便比较训练方案。
24. 作为训练者，我希望保存训练原模型与量化导出模型的对应关系，以便分别检查学习效果和导出保真度。
25. 作为训练者，我希望看到训练和验证误差，以便发现训练异常，但不把误差下降自动当作棋力提升。
26. 作为自主训练者，我希望正式版本能自己与自己完成对局，以便不依赖外部对手产生训练数据。
27. 作为自主训练者，我希望完整对局结束后回填胜负，以便用实际结果训练价值网络。
28. 作为自主训练者，我希望完全关闭教师后仍能采集和训练，以便最终摆脱 Rapfi 依赖。
29. 作为自主训练者，我希望自主训练退步时保留当前正式版本，以便训练失败不会破坏可玩的模型。
30. 作为测评者，我希望候选版本与冻结的旧版本对战，以便判断相对棋力是否进步。
31. 作为测评者，我希望同一开局交换黑白并保持相同思考时间和线程资源，以便减小评测偏差。
32. 作为测评者，我希望评测对局不进入正在被评测的候选模型训练，以便保持结果独立。
33. 作为测评者，我希望查看胜、和、负、得分率、有效对局数及异常，以便判断晋级结果是否可信。
34. 作为测评者，我希望晋级标准在比赛前冻结，以便不能看过结果后改门槛。
35. 作为用户，我希望新模型只有在评测通过后才成为默认对手，以便默认版本保持可靠。
36. 作为用户，我希望暂停、恢复和停止长任务，以便按自己的电脑使用安排训练。
37. 作为用户，我希望恢复任务时连同模型、优化器、样本池和运行进度一起恢复，以便不必重新开始。
38. 作为用户，我希望看到采集速度、有效样本数、训练进度、资源配置和测评结果，以便了解任务实际状态。
39. 作为维护者，我希望重用已有执行器、搜索和推理基础，以便避免无必要的整体重写。
40. 作为维护者，我希望旧规格、旧工单和旧实验限制被清理，以便后续工作只服从当前设计。
41. 作为维护者，我希望新版本记录模型、数据、规则、搜索和依赖身份，以便复现结果。
42. 作为本机用户，我希望核心工作流离线可用，以便不依赖云端账户或在线服务。

## Implementation Decisions

本节区分已确认的产品方向与实施时需要冻结的技术参数。没有讨论定值的参数不得伪装成用户已批准的硬门槛，也不得继续继承旧实验数值。

### 1. 后端执行器与规则

- 固定 15×15，黑先白后，第一版自由开局，不实现比赛交换开局流程。
- 使用 Renju 禁手语义：黑方三三、四四、长连受到限制；黑方恰好五连获胜，白方五连及以上获胜。成五与其他棋形同现的优先级、真假活三及递归延伸合法性依据 RIF 规则核验，不能靠简单棋形计数替代。
- 提供局面重建、规则校验、完整合法落点查询、落子、撤销和终局结果能力。搜索候选裁剪与完整合法落子集合必须区分。
- 对局、采集和比赛裁判共用规则实现。裁判不能只检查长连，也不能依赖参赛引擎自行过滤三三、四四。
- 终局后禁止继续落子；拒绝非法落子不能改变棋盘、行棋方、历史或累加器。
- 复用现有实现，但以新行为验收；已有代码存在不代表规则已经完全正确。

### 2. 开源 VCF 与战术边界

- 必须复用开源算杀，不把现有自研 VCF 当作新方案的最终实现，也不另写一个 VCF 算法。
- 所选实现必须支持本项目的禁手规则。实施前核验上游版本、许可证、依赖和可调用能力，并通过适配层接入；不预先假设 Rapfi 的 VCF 是独立库。
- 适配结果至少区分已证明结果、预算内未找到证明、预算耗尽或中断、输入错误；保留首着、可复查的变化或证据以及搜索预算。
- 只有已证明的算杀结果可以覆盖常规价值评估。未找到 VCF 不表示不存在 VCT 或其他强制获胜手段。
- 阶段二同时服务实际搜索与训练样本过滤；不以教师返回的任意数值直接充当杀棋证明。
- VCF 在搜索中的调用位置和预算通过实测选择，不继承旧版本只在根节点调用的限制。

### 3. Rapfi 教师与数据打标

- 教师优先作为独立本地进程运行，通过版本化适配器同步局面、规则、搜索预算并获取可核验的评分。
- 必须先确认所用 Rapfi 版本及权重确实支持 Renju；教师可执行文件和权重均记录身份。
- 教师分数、当前模型分数与最终胜负是不同标签来源。原始分数、原始视角、归一化规则和标签版本必须保存，禁止直接混用。
- 教师 mate 分、已结束局面、已识别算杀局面和异常响应不作为普通静态评分样本。预算耗尽与其他未知情况单独计数，默认不放入教师训练队列。
- 初版对“过滤算杀阶段”的可实现定义为：基于可用战术证据排除已识别强制局面；不声称有限 VCF 搜索能证明剩余数据绝无算杀。
- 样本记录覆盖盘面、规则、行棋方、对局身份、实际着法、采集模型身份、标签来源和版本、战术筛选状态及最终胜负。未完成对局的胜负不得伪造为和棋。
- 旧记录格式是否足以承载新契约需要审查；必要时升级格式并明确拒绝误读，不要求兼容旧实验数据。

### 4. 持续采集与滚动样本池

- 不要求先积累500万～2000万条；小批量启动后，采集、打标和训练可作为独立任务持续推进。
- 区分累计生成、过滤后有效、去重后有效、当前池容量、实际训练曝光和对称增广次数；八种对称不能算八个独立原始局面。
- 样本池容量、启动样本量、新旧样本比例、探索强度、训练与采集速率均可配置。先测吞吐和链路正确性，再确定本机默认值。
- 从多个完整对局混合采样并进行去重或重复控制，避免立即只训练刚走出的相邻局面。池满后按明确策略逐步淘汰旧样本，保留策略与数据身份。
- 训练者只读取已提交、完整且通过校验的数据；读取中的分片不会被原地删除。采集过快时限速或暂停，不能无限扩大磁盘占用。
- 验证集身份独立冻结，按对局隔离，并检查 D4 等价局面泄漏；新数据追加或池淘汰不能悄悄重抽验证集。
- 最初的小规模运行用于核验规则、标签、数值链路和成本，不要求小数据模型必须先提升棋力才允许扩大采集。

### 5. PyTorch 模型、价值语义与导出

- 网络主干固定为 450 → 1024 → 64 → 32 → 1。450 对应两个各225格的占位通道，单输出头；不沿用旧的15维隐藏层和双输出头结构。
- 输入必须保留 Renju 的黑白角色差异。实施默认采用绝对黑白通道，行棋方随样本记录并检查其与合法轮次一致；不把交换黑白当作合法对称增广。
- D4 八种旋转与镜像在线增广，只变换空间，不改变黑白角色。训练集与验证集共用明确的价值视角契约。
- 价值视角、教师分数归一化、网络输出映射和搜索分数转换必须作为同一数值契约冻结。工程默认建议为黑方绝对价值，进入 negamax 时按行棋方转换；这属于实施默认值，不是额外增加输入或输出头的授权。
- 教师启动回归归一化后的教师价值；自主训练回归同一价值空间中的实际结果，黑胜、和棋、白胜分别为正、零、负目标。MSE 与 SmoothL1 均可配置并记录。
- 过渡期如混合教师与结果监督，必须记录两种标签的尺度和权重，不能直接把原始引擎分与正负一混合。
- 先建立训练原模型到部署模型的保真度报告，再优化量化和 SIMD。新网络采用可识别的新模型格式或版本，拒绝把旧权重按新布局解释。
- 导出模型包含架构、规则、特征、价值契约和校验身份；加载失败必须明确报告，不能静默使用手工评估后仍把结果标作 NNUE。

### 6. C++ 增量累加器与 Alpha-Beta

- 在执行器中集成新网络推理；第一层使用稀疏增量累加器，落子加上对应特征向量，撤销减去同一向量。
- 向量加减只更新第一层状态；后续64、32和单输出层仍执行前向计算，不能把整网评估描述为只有向量加减。
- 累加状态与棋盘、撤销栈及局面同步一致。使用足够宽的内部表示或可逆状态保存，避免累加器饱和导致撤销失真。
- 保留全量重建与标量参考推理，作为增量和 AVX2 实现的数值参照。
- 搜索复用 Alpha-Beta 基础，整合合法落子、终局、VCF、价值评估与时间控制；保留可复现的搜索资源配置。
- 搜索速度提升和棋力提升分别测量。正式版本在没有可用模型时不得伪装成模型已就绪。

### 7. 教师退出与自主训练

- 教师是启动手段，不是永久依赖。初始正式版本 v0 跑通完整合法对局、训练、导出和评测后，即可开始独立自主训练试验。
- 自我对弈使用明确的模型快照；候选模型在独立训练过程中更新，不把每个优化步骤直接覆盖到正在进行的对局中。
- 对局按规则完成后回填真实胜负；可以筛掉不适合价值训练的战术局面，但必须保留整盘结果。崩溃、超时或人为截断不得当作自然终局训练标签。
- 自主训练需要探索多样开局和走法，并混合适量历史样本。具体探索和重放配置需记录，不承诺每轮都能进步。
- 不采用“模型给局面打原始分，再原样训练自己”作为有效自主学习机制；从实际胜负获得新增训练信号。
- 可以先停止新增教师标签而暂用教师历史样本过渡，随后进入完全无教师样本更新的阶段。两种状态必须分别显示，不能都称作完全无教师。
- 无教师候选与冻结的正式版本进行独立测评，通过后晋级；失败保留正式版本，可以调整训练或恢复教师启动训练。
- 正式停用教师依据无教师循环的可运行性和相对历史版本的进步证据，不依据固定数据量，不要求战胜 Rapfi，也不保证已达到教师棋力。

### 8. 测评与版本晋级

- 两类训练分别是教师评分学习和自主胜负学习；棋力测评是候选版本挑战历史版本。同一版本左右互搏只产生数据，不能单独证明进步。
- 区分训练误差、独立验证误差、算术一致性、导出保真度和实战棋力，分别出报告。
- 棋力比较采用冻结模型、配对开局、交换黑白、相同思考时间及线程资源；测评对局与候选训练隔离，开局来源和身份可复查。
- 晋级配置在开赛前固定，包含有效局数或停止规则、得分率门槛、统计判断方式和异常处理；不继续使用旧 M5 的65%或固定深度门槛。
- 同时报告胜、和、负、严格胜率、得分率、区间或预定的统计结论、用时和异常。少量偶然获胜不足以自动宣告提升。
- 裁判识别禁手、非法落子、崩溃、超时和模型加载失败，区分棋局判负与有效晋级证据。异常对局不得制造“棋力提升”。
- 晋级按已冻结配置执行；失败或评测未完成都不替换正式版本。连续使用同一评测集合时需控制对评测集的过拟合。
- 从新流程的 v0 建立新历史，保留当前正式版本、晋级来源和必要的冻结对手。用户已允许删除旧项目历史，不要求迁移旧权重。

### 9. GUI 与任务编排

- 交付本机桌面 GUI，覆盖“玩一把”“收集数据”“从0训练”“自我训练”“测评”和模型选择。
- GUI 只负责交互与任务管理，规则、采集、训练和评测共用后端能力，避免在界面重复实现规则。
- 后台任务提供稳定的启动、状态、暂停、恢复和停止接口；GUI 不因长任务阻塞。
- 暂停在安全的数据或训练检查点生效，界面区分运行、暂停中、已暂停、完成、失败和已停止，不能只改变按钮文字。
- 恢复记录模型与优化器、随机状态、训练进度、样本池与任务配置；停止后回收所启动的工作进程，避免后台遗留任务。
- 训练模型发布是版本化操作；只有经过数值检查和晋级流程的候选才能替换默认正式版本。
- GUI 框架、控制协议和具体控件布局尚未选定；实施时选择能够复用本地进程与 PyTorch 的方案，不将特定框架写成已有共识。

### 10. 交付顺序与旧内容清理

- 第一步：验证并整理后端执行器，覆盖棋盘、判赢、完整合法落子和禁手。
- 第二步：选择并接入开源 VCF，建立战术适配与筛选边界。
- 第三步：接入 Rapfi 教师，形成少量启动数据和持续采集样本池。
- 第四步：实现新 PyTorch 网络、D4 增广、训练验证与部署导出。
- 第五步：实现基于自我对弈胜负的自主训练与历史版本晋级。
- 第六步：完成新网络的 C++ 增量累加器、Alpha-Beta 集成和性能优化，并整合 GUI 工作流。
- 阶段顺序是交付主线，不禁止必要的前置集成：第五步开始前必须已有可对弈的新模型 C++ 推理，不能把所有模型部署都拖到第六步之后。
- GUI 控制能力可随阶段逐步接入，最终必须统一到客户端。
- 清除被本规格取代的旧规格、旧 README 内容、旧工单和诊断历史。实现代码以新契约审查后复用或替换，不能凭文件名批量删除共享基础。
- 不把旧 M5 未通过、旧诊断预算、旧最终模型冻结规则作为本轮隐含阻塞。

## Testing Decisions

- 只断言外部可观察行为，不根据函数拆分、内部缓存布局或代码行数编写镜像测试。
- 最高层验收优先复用现有引擎协议和真实进程工具链：小规模采集 → 标签或结果入池 → 训练 → 导出 → 加载 → 完整对局 → 候选评测 → 晋级或保留正式版本。
- GUI 新增一个公共任务编排边界，测试任务启动、状态、暂停、恢复、失败和进程清理；实际工作由既有后端接口承担。界面验收覆盖用户可见流程，不另造一套引擎行为。
- 规则例外保留棋盘公共 API 接缝：非法落子状态不变、真假活三、四四去重、长连、成五优先、白棋长连、终局拒绝落子以及 D4 下规则一致。参照现有棋盘和 Renju 测试，结合 RIF 规则题例补齐，不把旧测试通过当作规则完整证明。
- VCF 在适配器公共边界验证已证明杀棋、合法防守、禁手相关变化、未证明、预算耗尽和停止；证据可由执行器复查。限额退出不得误报确定结论。
- 数据在写入与读取的公共边界验证标签视角、规则身份、分片完整性、结果回填、样本来源、未知隔离、池淘汰与读取并发、对局隔离及 D4 泄漏。沿用现有数据生成和冻结验证测试的可复现素材。
- 模型在导出文件边界验证架构和版本拒绝、全量与增量推理一致、连续落子撤销后状态恢复、标量与 AVX2 一致，以及训练原模型到部署模型的保真度；沿用现有推理 probe 和跨语言对拍方法。
- 晋级在对战 runner 边界验证配对换色、公平资源、冻结配置、实际模型身份、异常处理、失败不晋级、通过后版本切换；不以教师对战代替历史版本测评。
- 增加无教师验收场景：阻断或移除 Rapfi 可执行文件后，自主模式仍能完成自我对弈、结果训练、导出和历史测评；教师模式则明确报依赖缺失。完全无教师阶段还须验证不再抽取教师来源标签。
- 小规模真实闭环检查正确性和成本，不宣称证明模型容量、最终棋力或百万级吞吐；棋力实验与代码正确性测试分别报告。

## Out of Scope

- 战胜 Rapfi，或将教师对战胜率作为模型交付与晋级门槛。
- 先攒满500万～2000万条才允许训练，以及永久保留全部累计数据。
- 自研 VCF 算法、完整 VCT 求解或证明所有保留局面绝无强制杀棋。
- Renju 比赛交换开局、其他棋盘尺寸、联网对战、云端训练和跨平台发布。
- 将工程改成 AlphaZero 的策略价值双头加 MCTS；本轮保持单价值网络与 Alpha-Beta。胜负训练本身不要求采用 MCTS。
- 承诺每次训练都变强，或仅凭损失下降、数值一致宣布棋力提升。
- 兼容或恢复旧实验数据、旧权重、旧工单编号和旧 M5/M6 依赖。
- 本次文档更新直接完成引擎、GUI、Rapfi 接入、新模型或训练流程的实现。
