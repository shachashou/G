## Progress Notes

> *This was generated by AI during triage.*

技术三项已交付并验收（`ctest` **14/14 全绿**，11.38 秒；引擎版本 `0.9.0`）；**M5 胜率门控实测未达标，工单保持 in-progress，M5 里程碑尚未达成**。

- **AVX2 实现（`engine/src/nnue.cpp`）**：累加器仍是 `int32[1024]` 的精确和（不做中间饱和），落子/撤子用 `_mm_loadl_epi64` + `_mm256_cvtepi8_epi32` 把 8 个 int8 权重扩成 8 个 int32 lane，一次 `_mm256_add/sub_epi32` 完成差分更新。后段 L1 也向量化：加载时把 `W1[1024,15]` 补成 16 字节/行存进 `w1Padded_`，推理时用两组 8-lane 向量累加器算 `z[k] = Σ_j a[j]*W1[j,k]`（第 16 lane 恒为 0，直接丢弃），`_mm256_mullo_epi32` 乘 `a[j]`。所有 `round_div` / ClippedReLU / int16 饱和与双头逻辑与标量路径共用，因此**切换后端不改变任何一个 bit**。
- **逐位对拍**：`nnue_tests.cpp` 在 10 步落子/撤子序列上逐步比较两后端；`engine/tests/nnue_backend_tests.py` 在 24 个采样局面上比较 `features` / `infer`（全量稀疏）/ `board`（增量累加器）三种输出，scalar 与 AVX2 都逐位等于 `weights_format.infer_int()`，且彼此逐位相等。工单 09 的跨语言 parity / 黑盒完整对局在默认 AVX2 后端下依旧全绿（PyTorch float vs C++ `max 0.7367 ≤ 2`）。
- **单次评估耗时（本机实测，`nnue_probe bench`，20,000 次/后端，含 1000 次预热）**：标量 **3,117.55 ns/eval**，AVX2 **1,154.87 ns/eval ≈ 1.15 µs**，**2.70×** 加速，达到微秒级且不成为搜索瓶颈。`volatile` 读阻止编译器把循环提出去。测试断言 AVX2 < 20 µs 且至少比标量快 5%。
- **三档后端切换**：无 `--nnue` = 手工评估；`--nnue PATH` 默认 AVX2；`--nnue-backend scalar|avx2` 显式选择。`ABOUT` 输出 `eval=` 与 `nnue_backend=`（`none` / `scalar` / `avx2`）；未知后端名在 stderr 警告并回退 AVX2；坏/缺失权重回退手工评估，stdout 协议流不受污染。`nnue_probe --backend` 提供同款开关供离线对拍。
- **M5 门控实测（未达标）**：`match_runner --games 100 --rule 2 --opening-plies 2 --seed 20261105 --min-win-rate 0.65`，A = `gomoku_nnue.exe --nnue weights\nnue_v1.nnue --depth 2`，B = `gomoku_nnue.exe --depth 2`（相同搜索配置，M3 基线 = 手工评估 + VCF）。结果 **A 0W / 0D / 100L，score rate 0.00% < 65%，门控退出码 2**，`anomalies: none`（不是超时/崩溃/非法着法），完整记录留在 `data/m5_gate.json`。20 局摸底同样 0/20。
- **根因诊断（不是 AVX2 或接入 bug）**：① 训练标签 `bench-d4/train.binpack` 的搜索分极端——7,208 条里 **17.9% 是 ±32767 饱和分**，p5 = -28,353 / p95 = +32,767，只有 19.7% 落在 ±600；而 `MSE(tanh(eval/400), tanh(score/400))` 对这类标签几乎饱和。② 导出的 v1 权重在 64 个采样局面上输出仅 `[-185, 30]`（均值 -92.75），与标签 MAE **13,647.7**，评估缺乏区分度与胜势表达能力。③ 把训练从 20 epoch 延长到 100 epoch（val loss `0.854 → 0.797`、MSE 仍 0.615）后输出仅扩到 `[-166, 105]`，20 局胜率 0% → 5%，说明不是训练轮数问题。④ 定点局面复现：对手活四时 NNUE 引擎与 M3 引擎给出**相同**着法，两引擎搜索行为一致，确认 `--nnue` 接入正确；差距来自权重本身。⑤ 工单 08 的交接已预告："首轮权重只用 7,208 个基准局面训练，棋力尚弱，M5/M6 需用 1000 万局面数据重新训练并做胜率门控"。
- **补充实验（本轮）**：① `trainer/` 新增可选 `--score-clip N`（默认 0 关闭，`dataset.clip_score()`），把 ±32767 饱和分裁剪到 ±N 后再进 `tanh`，**损失形式与权重文件格式均不变**；`training_tests.py` 覆盖默认行为不变、裁剪边界、dataset/iter_samples 一致性与 CLI 记录。② 三组 100-epoch 重训对照：不裁剪 val `0.797` / mse `0.615`（20 局胜率 5%）；`--score-clip 600` val `0.690` / mse `0.564`，eval 仍 `[-168, 79]`（20 局 0%）；再加 `--quant-reg 0 --lr 0.3` 反而 val `0.764` / mse `0.646`。③ 定量诊断：裁剪后目标方差 `0.671`（即「常数预测」的 MSE 基线），最好 val_mse `0.564` = 基线的 **84%**，模型只解释约 16% 的目标方差，接近常数预测。**结论修正**：瓶颈不只在标签尺度，更在 450→1024→15→1 量化架构对这批搜索分的表达能力 / 训练目标设计；仅补数据或清洗标签不足以让 M5 达标。
- **最终模型的落点（本轮补齐的规划）**：`spec.md` 与工单 11 已明确——训练是循环内重复动作，没有独立的「最终训练」阶段；M5 门控通过后产生第一个 incumbent，M6 每轮门控晋级，至少 3 轮且连续 2 轮未晋级即收敛，把当时的现任权重冻结为 `weights/final.nnue` 并写 `final_manifest.json`。最终模型 = 被门控保留的最后一个晋级版本，不是最后一轮训练产物。
